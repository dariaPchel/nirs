# Предварительная архитектура

## 1. Назначение
Документ описывает предполагаемое устройство прототипа FRAUDI. Архитектура предварительная и может уточняться после выбора технологического стека и проверки доступности LLM.

## 2. Логические компоненты

### 2.1. Пользовательский интерфейс
Предоставляет поле для описания ситуации, отображает уточняющие вопросы и показывает результат анализа. На контрольной точке 1 допускается локальный макет с демонстрационными данными.

### 2.2. Координатор диалога (агент)
Получает описание пользователя, определяет, каких сведений не хватает, формирует уточняющие вопросы и управляет последовательностью обработки. После уточнений передаёт поисковый запрос компоненту поиска и использует полученные документы при подготовке ответа.

В первой версии агент не выполняет финансовые операции, не блокирует счета и не связывается с третьими лицами.

### 2.3. Компонент поиска
Принимает запрос и возвращает наиболее релевантные документы из локального корпуса. Поиск реализуется методом BM25; индекс и расчёт релевантности разрабатываются командой в соответствии с требованиями НИРС.

### 2.4. Корпус документов
Содержит материалы о типичных сценариях мошенничества, признаках риска, правилах безопасного поведения и действиях после возможного инцидента. Документы должны иметь устойчивые идентификаторы и понятные названия.

### 2.5. Компонент генерации ответа (LLM)
Получает описание ситуации, ответы на уточняющие вопросы и найденные фрагменты документов. Формирует понятный ответ с оценкой риска, обоснованием, рекомендациями и оговоркой об ограничениях.

### 2.6. Проверка качества
Набор тестов проверяет пользовательские сценарии и формат ответа. Benchmark отдельно оценивает качество извлечения документов и, при наличии эталонных ответов, качество итоговой оценки ситуации.

## 3. Основной поток данных
1. Пользователь отправляет описание ситуации через интерфейс.
2. Координатор определяет, хватает ли сведений для анализа.
3. Если нет, координатор возвращает уточняющий вопрос; пользователь отвечает, и контекст дополняется.
4. Координатор формирует поисковый запрос.
5. Компонент BM25 возвращает top-k документов.
6. Найденные фрагменты передаются LLM вместе с описанием ситуации.
7. LLM формирует структурированный результат.
8. Интерфейс показывает оценку, причины, рекомендации и доступные источники.

## 4. Предлагаемый формат результата
```json
{
  "risk_level": "high",
  "summary": "Высокий риск мошенничества",
  "indicators": [
    "Собеседник представился сотрудником банка",
    "Собеседник запросил код из СМС"
  ],
  "recommendations": [
    "Не сообщать коды подтверждения",
    "Завершить подозрительный разговор",
    "Связаться с банком через официальный канал"
  ],
  "sources": [
    {
      "document_id": "example-document-id",
      "title": "Название материала"
    }
  ],
  "limitations": "Оценка основана на описании пользователя и найденных материалах"
}
```
Это пример логической структуры, а не утверждение о реализованном API. Допустимые значения `risk_level` и точный формат будут уточнены при реализации.

## 5. Принципы безопасности и надёжности
- Не считать утверждения собеседника доказанными только потому, что они приведены пользователем.
- Не утверждать, что конкретный человек совершил преступление.
- Разделять факты из описания, найденные сведения и вывод модели.
- Не придумывать источники, правила или цитаты.
- Если пользователь уже передал код или деньги, сначала показывать срочные действия.
- Не запрашивать пароли, полные данные карты и коды подтверждения.
- Использовать демонстрационные данные в макете и тестах.
